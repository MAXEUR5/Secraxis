# Secraxis Vault Manager — Cryptographic Profiles

Status: living document. Every profile ID here is serialized into the `.seis`
public header and authenticated (AAD / manifest binding); parsers accept only
registered IDs. There is no silent downgrade path.

---

## 1. KDF profiles (Argon2id, RFC 9106)

| Profile | ID | Memory | Iterations | Lanes | Salt | Output |
|---|---|---|---|---|---|---|
| KDF-Floor-v1 | 1 | 384 MiB | 3 | 4 | 32 B | 64 B |
| KDF-Default-v1 | 2 | 512 MiB | 4 | 4 | 32 B | 64 B |
| KDF-Strong-v1 | 3 | 1024 MiB | 5 | 8 | 32 B | 64 B |

Implementation: PHC reference implementation (`phc-winner-argon2`, pinned —
see `third_party/PIN.md`) via the low-level `argon2_context` API with a custom
arena allocator (best-effort `mlock`/`VirtualLock`, no-dump hints, guaranteed
wipe on release). libsodium's `crypto_pwhash` was rejected for the KDF because
it hardcodes `p=1` and a 16-byte salt, which cannot express these profiles.

KATs: three reference-suite vectors run in
`tests/unit/test_crypto_selftest.cpp` (`argon2id_reference_kats`) in every
test run. Anything weaker than KDF-Floor-v1 read from a file is rejected.

## 2. Key hierarchy (agenda §6)

```
master password
  -> Argon2id(profile, salt32) -> KEK_material_512 (64 B)
  -> HKDF-SHA-512 extract/expand, domain-separated -> KEK_wrap_key_256
     (salt: kdf_salt; info binds vault_id, format_version, KDF and AEAD
     profile ids)
  -> AEAD-unwrap VMK envelope -> VMK_512 (64 B, generated by OS CSPRNG at
     vault creation; never derived from the password)
  -> HKDF-SHA-512 extract (salt: label || vault_id) -> PRK
  -> HKDF-SHA-512 expand, domain-separated subkeys (manifest key and nonce,
     page keys and nonces, runtime root), each bound to
     label || format_version || vault_id || epoch || save_salt || index
     (index = page_index for pages; the runtime root also mixes in a fresh
     random value per session, and the per-entry runtime keys derived from
     it an entry_id)
```

Profile ids and the rest of the header are bound through the AEAD AAD of the
manifest and of every page (`SEIS_FORMAT.md` §2), not through the subkey
derivation. There are no export, A2ONT-context or padding subkeys: the
A2ONT context is a public byte string built from the header (§4,
`A2ONT_INTEGRATION.md` §3), and padding bytes come from the random-number
mixer (§5). `crypto_profile.h` also defines the labels `seis-header-auth-v1`,
`seis-export-v1` and `seis-padding-v1`; nothing uses them in 0.9.1.

HKDF-SHA-512 comes from libsodium (`crypto_kdf_hkdf_sha512`), verified against
a cross-implementation vector in every test run
(`hkdf_sha512_rfc5869_tc1_adapted`). 512-bit root material is used at
every layer that supports it; 256-bit subkeys are derived where the vetted
AEAD requires 256-bit keys (this is correct practice, not a weakness — agenda
§4.1).

## 3. AEAD profiles

| Profile | ID | Primitive | Key | Nonce | Tag | Status |
|---|---|---|---|---|---|---|
| SEIS-AEAD-2 | 2 | AES-256-GCM-SIV (**OpenSSL ≥ 3.2**, RFC 8452) | 32 B | 12 B | 16 B | **implemented — default for new vaults** (misuse-resistant profile) |
| SEIS-AEAD-1 | 1 | XChaCha20-Poly1305-ietf (libsodium) | 32 B | 24 B | 16 B | **implemented — portable/software profile & fallback** |

Directive (project owner, 2026-07-05): *prioritize AES-256-GCM-SIV as the
default vault-body AEAD; fall back to XChaCha20-Poly1305 only if GCM-SIV is
unavailable. Prefer **OpenSSL** for the GCM-SIV backend; AWS-LC is heavier.*
Outcome: **AES-256-GCM-SIV via OpenSSL is the default**; XChaCha20-Poly1305 is
the portable fallback; AWS-LC remains a validated, selectable alternative
backend. No fallback to XChaCha was needed on the supported platforms.

### 3.1 Decision record: GCM-SIV backend = OpenSSL (default), AWS-LC (alternative)

A vetted RFC 8452 implementation was required; hand-implementing it is
forbidden (agenda §4.3). Survey on the platform matrix (Windows x64 /
MinGW-GCC-14 local; Linux x64 / GCC on dot7, dot8):

1. **libsodium / Botan / mbedTLS / wolfSSL / Nettle(<3.9)** — no RFC 8452
   AES-GCM-SIV (Botan's "SIV" is AES-SIV RFC 5297, a different construction).
2. **OpenSSL ≥ 3.2** — **selected as default.** OpenSSL added AES-256-GCM-SIV
   in 3.2. It is the system libcrypto on most Linux distributions (so where
   that is 3.2 or newer, no vendored crypto is needed — a
   portability/scalability win the owner called out; Ubuntu 24.04 still ships
   3.0.13, so the Linux test host builds the pinned release), and it builds on
   Windows/MinGW once an MSYS-flavored Perl is available. Consumed via
   `EVP_CIPHER_fetch("AES-256-GCM-SIV")` + `EVP_{Encrypt,Decrypt}*`. Built
   minimal (`no-shared no-tests no-apps no-docs no-deprecated no-legacy
   no-engine no-module no-autoload-config`) so the linked surface is
   libcrypto-only and — importantly — the `no-autoload-config` flag disables
   the implicit `openssl.cnf`/`OPENSSL_CONF` loading that would otherwise be a
   local-attack surface for a security tool. Pinned by SHA-256 in
   `third_party/PIN.md`; reproducible via `scripts/build_openssl.sh`.
3. **AWS-LC v5.1.0** — **validated alternative** (`-DSECRAXIS_AWSLC_ROOT`).
   Audited BoringSSL lineage, one-shot `EVP_AEAD` API, smaller linked binary.
   Retained because it is useful for cross-backend interop testing and for
   environments that prefer it; not the default because of its heavier source
   footprint (below) and because OpenSSL is already present system-wide on
   most Linux systems (if not always at 3.2 or newer).
4. **BoringSSL** — origin of GCM-SIV, but no tagged releases + Go requirement;
   unsupported on MinGW. Rejected.

Verification: the five RFC 8452 C.2 official vectors (incl. the plaintext+AAD
case), a SIV-determinism check, and tamper-rejection tests run in
`tests/unit/test_crypto_selftest.cpp` in every test run, under whichever
backend is compiled in.

### 3.1.1 OpenSSL vs AWS-LC — measured comparison and why OpenSSL is default

Both implement RFC 8452 correctly and the SEIS-AEAD-2 wire format is
backend-independent: this is **tested**, not just asserted — `scripts/test_backend_interop.sh`
builds the identical `seis_interop_tool` source under each backend and shows a
GCM-SIV vault created by OpenSSL opens byte-exact under AWS-LC **and** vice
versa (both directions PASS, `aead_id=2`, content byte-identical). Measured on
this machine (2026-07-05, MinGW GCC 14.2):

| Criterion | OpenSSL 3.5.1 (**default**) | AWS-LC v5.1.0 (alternative) |
|---|---|---|
| Source tarball fetched | **51 MB** | 139 MB (~2.7× larger — the owner's stated concern) |
| Built static `libcrypto.a` | 9.0 MB | 3.6 MB |
| Final linked binary (same source) | 6.2 MB | 2.6 MB |
| Presence on Unix targets (dot7/dot8, macOS) | **System package** where it is ≥ 3.2 (dot8's Ubuntu 24.04 has 3.0.13, so the pinned 3.5.1 is built there; macOS: Homebrew) | Must be vendored+built |
| Windows/MinGW build | Works via MSYS2 Perl (build-time only, in `D:\OTHER_ENV`) | Works via vendored pregenerated sources (no Perl/Go) |
| Config/env attack surface | Neutralized at build via `no-autoload-config` (no `openssl.cnf`/env loading) | None by design |
| GCM-SIV lineage / field exposure | Added 3.2 (2023); newer | BoringSSL line since ~2017; more exercised |
| API used | `EVP_CIPHER` streaming (~95 lines) | one-shot `EVP_AEAD` (~45 lines) |
| KAT gate | RFC 8452 vectors pass | RFC 8452 vectors pass |

Decision: **OpenSSL is the default backend.** It is the smaller supply chain
(the owner's priority), it is already the system libcrypto on most Linux
distributions (so where that is 3.2 or newer, no vendored crypto is needed —
a real scalability/portability win), the Windows build blocker is resolved
with a **build-time-only** MSYS2 Perl living in `D:\OTHER_ENV` (never linked,
never shipped), and its one meaningful audit-surface drawback (implicit
config loading) is switched off at build. AWS-LC's advantages (smaller
binary, older GCM-SIV lineage, simpler API) are real but do not outweigh
these for a local-first tool whose Unix builds can often use the system
OpenSSL. AWS-LC stays fully supported as `-DSECRAXIS_AWSLC_ROOT` and is the
cross-backend interop oracle.

Historical note (kept per owner instruction — this is a *platform-specific
build decision, not a claim that OpenSSL is cryptographically unsuitable*): an
initial OpenSSL build attempt on native Strawberry Perl failed because
`Configure mingw64` requires an MSYS-flavored Perl; that was resolved by
provisioning MSYS2's Perl in `D:\OTHER_ENV` (a build-time toolchain the owner
explicitly authorized). AWS-LC was the interim default while that was pending.

Backend swap is a build flag only; the `.seis` on-disk format never changes
(checked by the interop test).

### 3.2 Profile selection & fallback rules

* **New vaults** default to SEIS-AEAD-2 (GCM-SIV) when the build carries a
  GCM-SIV backend (OpenSSL by default) that works at run time (an OpenSSL
  older than 3.2 links but has no GCM-SIV) and the CPU has AES-NI+CLMUL
  (constant-time hardware path).
* **Fallback to SEIS-AEAD-1** (XChaCha20-Poly1305) occurs only when: the
  build has no GCM-SIV backend (portable-only build), the OpenSSL it runs
  with is older than 3.2, or the CPU lacks AES-NI/CLMUL (where SIV would run
  on a software AES path we do not accept by default). The chosen profile is
  recorded in the vault header, authenticated, and never silently changed
  afterward.
* **Existing vaults** always use their recorded, authenticated profile; both
  profiles are first-class citizens with official KATs, so either kind of
  vault opens on any full build (one whose GCM-SIV backend works at run
  time; elsewhere a GCM-SIV vault is refused as unsupported before the key
  derivation, and the screen shows its one generic "Wrong password or
  corrupted vault."). On a CPU without AES-NI/CLMUL an AES-256-GCM-SIV
  vault still opens, through OpenSSL's software AES, which is not
  guaranteed constant-time (the reason new vaults avoid that path).
  Profile migration is only via the explicit upgrade
  workflow (agenda §15.11), which in 0.9.1 changes the KDF profile only: no
  command changes a vault's AEAD profile.
* XChaCha20-Poly1305 is not nonce-misuse-resistant in the SIV sense: a reused
  (key, nonce) pair would leak plaintext XOR and enable forgery. This risk is
  neutralized structurally (§3.3) — and those same rules are applied to the
  GCM-SIV profile too, making SIV's misuse resistance a second, independent
  safety layer rather than a crutch.

### 3.3 Nonce-misuse prevention (applies to BOTH profiles; defense in depth)

1. **Unique key per object, not just unique nonce.** Every page key is itself
   single-use: `page_key = HKDF-Expand(PRK, "seis-page-aead-v1" ||
   format_version || vault_id || epoch || save_salt || page_index)`, where
   `PRK = HKDF-Extract(VMK)` (§2). Two different encryptions never share a
   key, so nonce collision between them is cryptographically irrelevant.
2. **Derived nonces, no free-form nonce input.** Nonces come from the same
   domain-separated derivation (label "seis-page-nonce-v1" / manifest label);
   no code path accepts a caller-supplied nonce; no nonce is stored
   unauthenticated.
3. **Monotonic epoch.** Every save advances the epoch; the epoch is
   authenticated (manifest + AAD). A save can never re-encrypt under an old
   epoch.
4. **Per-save random `save_salt` (32 B, OS CSPRNG), stored in the public
   header and authenticated.** This kills the residual corner case that pure
   counter schemes have: a VM snapshot/process fork resumed twice would reuse
   `epoch+1` for two *different* vault states. Because each save mixes a fresh
   random salt into every key/nonce derivation, forked timelines diverge with
   overwhelming probability. (This is a deliberate hybrid of deterministic
   and random derivation.)
5. **VMK envelope**: a random nonce of the profile's length (24 bytes for
   XChaCha20-Poly1305, 12 for AES-256-GCM-SIV), drawn anew on every (re)wrap
   (create / password change / rekey / KDF upgrade). Every rewrap also draws
   a fresh KDF salt, so the wrap key itself is new each time: no (key, nonce)
   pair repeats, whatever the nonce length.
6. **Tests + red team.** A unit test (`key_hierarchy_distinctness_grid`)
   asserts pairwise-distinct (key, nonce) across an (epoch × page) grid and
   across simulated forked saves (two save_salts per epoch); the
   red-team plan (agenda §22.6 "nonce reuse attempt") attacks exactly this
   property.

### 3.4 Path to SEIS-AEAD-2 (AES-256-GCM-SIV)

Profile ID 2 stayed reserved (files declaring it rejected as unsupported)
until it had: a formal agenda revision selecting it (the owner's directive,
§3); a vetted library decision (BoringSSL/AWS-LC/OpenSSL≥3.2 trade study,
§3.1); RFC 8452 KATs wired into the tests (`aes256gcmsiv_rfc8452_vectors`);
and `.seis` tests for the new profile (the container roundtrip and tamper
suites run under it, and `scripts/test_backend_interop.sh` across both
backends; a `.seis` file has no fixed byte vectors, see
`tests/vectors/VECTORS.md`). The planned migration path via the
profile-upgrade mechanism (agenda §15.11) was not built: `upgrade` changes
only the KDF profile, so a vault keeps the AEAD profile it was created with.
A build without a working GCM-SIV backend still rejects files declaring AEAD
id 2 as unsupported — never silently accepted or downgraded.

## 4. A2ONT profile

v1 binds `A2ONT-v1.0-default` (profile id 1; 32-byte seed, 2 rounds,
GF(2^128) Cauchy threshold core) as specified by the module's own normative
spec (`docs/a2ont/A2ONT-SPEC-v1.0.md`). The 32-byte (256-bit) seed follows
agenda §4.2's explicit rule: the module's documented profile is used rather
than silently altering the module. `A2ONT-v1.0-strong` (id 2) is available
behind the same authenticated profile mechanism (such vaults open and save;
new vaults use the default profile). A2ONT is **not** encryption; it is a
reversible pre-encryption transform, and every A2ONT parameter that affects
decoding is authenticated via the manifest/AAD binding.

## 5. Randomness

Every random byte Secraxis uses (the VMK, salts, `save_salt`, vault and entry
ids, nonces, padding, the runtime store's keys, temporary file names) comes
from one function, `random_bytes` (`src/crypto/entropy.cpp`). Each call draws
two independent sources afresh and mixes them:

```
IKM  = OS[64] || RDSEED[64]                                   (128 bytes)
salt = lp("secraxis-entropy-mix-v1") ||
       lp("Every watcher lies alone; two liars cannot lie as one.")
PRK  = HKDF-Extract(salt, IKM)                                (HMAC-SHA-512)
info = lp(label) || le64(counter) || le64(time-stamp counter) || le64(process id)
out  = HKDF-Expand(PRK, info, n)       n <= 16,320; label "secraxis-entropy-out-v1"
     = ChaCha20 keyed by HKDF-Expand(PRK, info, 32)    longer outputs (padding);
                                       label "secraxis-entropy-stream-v1"
```

- **OS source:** libsodium's `randombytes_buf` (RtlGenRandom on Windows,
  `getrandom()` on Linux), 64 bytes per call. It aborts the process rather
  than return less.
- **Hardware source:** the CPU's RDSEED, 64-bit form, 8 words per call. A
  "not ready" answer is retried after a pause (about five tries per word on
  the test machines); a word that takes longer than 100 ms counts as RDSEED
  having stopped.
- **Health checks** (any failure is final until the program restarts):
  - start-up self-test: 64 words, none repeated, each with at least 2 zero
    and 2 one bits, and 2048 ± 256 one bits over the 4,096 (8 standard
    deviations);
  - every word: at least 2 zero bits and 2 one bits (a healthy source trips
    this about once in 10^17 words);
  - no word repeated within a draw, or equal to the previous draw's last.

  A check is an alarm, not a filter: no word is discarded and redrawn, so
  the checks never shape the output.
- **No fallback.** Without RDSEED (CPUID reports none: processors before
  Intel Broadwell or AMD Zen, or a virtual machine that hides it) or after a
  failed check, every draw fails and the operation that needed it is
  refused (`Err::RngFailed`): opening, creating, changing and saving a vault
  alike. Nothing is ever made from the OS source alone. Opening and key
  changes are refused before the password is tried, so the refusal says
  nothing about the password.
- **Why it holds.** The output is unpredictable if either source is sound,
  and a broken or hostile source cannot cancel the other without breaking
  SHA-512 (as it could under XOR). The counter, time-stamp counter and
  process id claim no entropy and stay out of the IKM: they only make clones
  of one process diverge (a copied virtual machine resumed twice) should
  both sources repeat.
- **The salt's verse** is a public constant that only names the context; it
  replaces no entropy and never reaches a stored key's derivation, so it may
  change in any release. Its second line salts the runtime store's PRK
  (`RUNTIME_MEMORY_SECURITY.md` §4).
- **A2ONT's seed** comes from the OS generator inside the A2ONT component
  (BCryptGenRandom / getrandom). It is hidden inside the AEAD and carries no
  security, and a save draws from the mixer (`save_salt`, padding) before
  A2ONT runs, so no save happens without RDSEED either.
- **Cost:** RDSEED takes about 9 to 15 µs per draw (measured: 8.6 µs on the
  Xeon test host, 14.9 µs on a Core i7-12700), so opening a 5,000-entry vault
  takes about 0.2 s more.
- **Verification** (`test_crypto_selftest`, `test_vault_session`): the
  construction's exact bytes against an independent libsodium computation
  (expand and stream paths); every input's effect on the output; the health
  checks on built word streams; refusal without RDSEED (opening, creating,
  key changes, saving, editing: nothing written, entries kept whole). Each
  was mutation-checked.
