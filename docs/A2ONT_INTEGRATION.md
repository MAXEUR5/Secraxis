# A2ONT Integration

How A2ONT is built into Secraxis Vault Manager. Read alongside the normative
algorithm spec, `docs/a2ont/A2ONT-SPEC-v1.0.md`.

## 1. What A2ONT is, and is not

A2ONT (Avalanche All-or-Nothing Transform) is a **reversible, randomized,
seed-hidden, AONT-derived pre-encryption encoding transform**. In Secraxis it
runs on the padded canonical vault body *before* AEAD. It is **not**
encryption, not a MAC, not a cipher: given a complete A2ONT output and the
public context, it is reversible without any secret key. Therefore Secraxis
**never** relies on A2ONT for confidentiality or integrity — AEAD does that,
always, applied after A2ONT.

Its role (agenda §2, §10): reduce structural locality, update-pattern
clarity, and parser-observable formatting before encryption, and provide
AONT-style whole-output dependency (any missing output bits corrupt recovery
of the seed and hence the whole plaintext).

## 2. A2ONT is part of Secraxis

A2ONT's C implementation lives in this repository and compiles straight into
`secraxis_core`, under the same `-Werror` warning and hardening flags as the
rest of Secraxis. There is no separate library, adapter layer, or pluggable
seam: the `.seis` container calls the A2ONT API directly (§3).

| Path | Contents |
|---|---|
| `src/a2ont/` | the algorithm (16 C files + internal headers) |
| `include/secraxis/a2ont.h` | its C API |
| `tests/a2ont/` | the component's own suites (vectors, roundtrip, decode/header fuzz, the `a2ont.hpp` C++ wrapper test) and the `bench_a2ont` throughput tool |
| `tests/vectors/a2ont/` | 21 cross-language vectors, generated by the Python reference implementation |
| `docs/a2ont/` | the normative spec and the design/security-claims document |

The two `tests/` folders belong to the development tree, not the public
source.

**Provenance.** Imported from the A2ONT project at commit
`5ac22b58f7fc0d6e9b301f4a0492b31232443441`. At import every file was
byte-identical to that commit except the `#include "a2ont.h"` lines, which now
read `#include "secraxis/a2ont.h"`. The Python reference implementation and
the statistical experiment campaign behind the vectors, and the A2ONT
project's v2 evaluation reports (cited by `docs/a2ont/DESIGN_AND_SECURITY.md`),
were not imported.

**Changing `src/a2ont`.** The 21 vectors pin the output byte-for-byte, and
every existing vault depends on that output. A change that alters any vector
is a `.seis` format change, not a refactor.

**Test-only flavor.** The vector tests need A2ONT's caller-chosen-seed entry
points (`A2ONT_TEST_ONLY`). `tests/CMakeLists.txt` builds a separate
`a2ont_testonly` library from the same sources, linked only into the A2ONT
tests and `bench_a2ont`. `seis_container.cpp` refuses to compile if
`A2ONT_TEST_ONLY` ever reaches `secraxis_core`, and release binaries contain
none of those symbols. The
`a2ont.hpp` wrapper throws exceptions and returns `std::vector` output, which
breaks Secraxis's memory rules, so it stays test code.

## 3. The A2ONT stage of the `.seis` container (`src/seis_format/seis_container.cpp`)

A2ONT's API is vault-agnostic. The code that binds it to a vault lives in the
container, next to the save and unlock pipelines that use it. It does five
things, none of which touch the algorithm:

1. **Profile whitelist** — only Secraxis's authenticated `A2ontProfileId`
   values (1=default, 2=strong) resolve, through an explicit switch. The A2ONT
   code also defines weakened research/ablation profiles (ids 3–9: r1,
   no-core, no-bitpremix, xor-chains, no-ar32, sym256, perbyte-bpm); a file's
   id is never handed to `a2ont_profile_init` unchecked. The header parser
   independently rejects every id except 1 and 2.
2. **Context construction** (security-critical) — builds the opaque `ctx`
   byte string A2ONT binds into its seed-hiding hash, canonically from the
   vault's authenticated identity:
   `"seis-a2ont-context-v1" ‖ format_version ‖ vault_id ‖ epoch ‖ save_salt ‖
   padded_len ‖ a2ont_profile_id ‖ aead_profile_id ‖ padding_policy_id ‖
   canonical_version`. This is agenda §10.3 binding: A2ONT output moved
   between vaults, epochs, or profiles never decodes to the original bytes,
   even before AEAD is considered (a profile mismatch is refused; under a
   wrong context A2ONT, which authenticates nothing, may still "decode", but
   to other bytes). This is defense in depth; AEAD remains the real boundary.
3. **Container placement** — stores `a2ont_header ‖ Y ‖ Y_extra` as the paged
   body; validates the header against the expected profile at decode;
   `seis_a2ont_body_len()` gives the save planner exact sizes up front.
4. **Memory policy** — A2ONT output is plaintext-equivalent, so it lives in
   `SecureBuffer` end-to-end and intermediates are wiped.
5. **Error collapsing** — A2ONT's typed errors
   (`A2ONT_ERR_INVALID_PROFILE`/`A2ONT_ERR_DECODE_FAILED`/…) collapse to the
   single generic failure on the unlock path (no parser oracle).

`seis_a2ont_decode()` is declared in `seis_container.h` so the `fuzz_a2ont`
target and the tests can reach it directly. Production code reaches it only
through unlock, validate, and save's pre-rename verification.

Agenda §16.2 lists a separate `A2ontBridge` component. By owner decision
(2026-10-30) it was folded into the container; its five responsibilities
above are unchanged, and the on-disk format is byte-compatible in both
directions with vaults written before the change.

## 4. Placement in the pipeline

```
Save:   canonical bytes -> pad to bucket -> A2ONT (fresh CSPRNG seed) ->
        a2ont container -> split into 64 KiB pages -> AEAD each page

Unlock: AEAD-open pages -> reassemble a2ont container -> A2ONT inverse ->
        remove padding -> canonical parse
```

Every save uses a **fresh A2ONT seed** (generated inside `a2ont_encode` from
the OS CSPRNG) and a new epoch + save_salt, so two saves of identical content
produce unrelated A2ONT outputs and unrelated ciphertext.

## 5. Seed length (256-bit, per the module's spec)

A2ONT v1.0's normative profile uses a **32-byte (256-bit) seed**. Agenda §4.2
explicitly directs using the module's documented profile rather than silently
altering it, so Secraxis binds `A2ONT-v1.0-default` (32-byte seed, 2 rounds,
GF(2^128) blockwise-Cauchy threshold core). Secraxis uses **512-bit** root
material at the layers that support it (Argon2id output, KEK, VMK), and
256-bit subkeys where the AEAD requires them — the A2ONT seed size is set by
A2ONT's spec, not by Secraxis.

## 6. Tests (agenda §10.4)

- The production A2ONT objects in `secraxis_core` link and round-trip
  (`test_crypto_selftest: a2ont_production_link_and_roundtrip`).
- Both `.seis` profiles go through the whole pipeline: default in
  `container_create_unlock_save_roundtrip`, strong in
  `container_roundtrip_strong_a2ont_profile`.
- Fixed-seed reproduction of the 21 cross-language vectors (`a2ont_vectors`),
  plus the component's roundtrip, decode/header fuzz and C++ wrapper suites
  (`a2ont_roundtrip`, `a2ont_fuzz`, `a2ont_cpp`).
- Fresh seed per save: production builds cannot pass a seed (`a2ont_encode`
  draws its own), and `container_create_unlock_save_roundtrip` checks that
  two saves of identical content differ.
- Context layout, profile whitelist and length/framing checks
  (`a2ont_stage_context_binding_and_profile_whitelist`). It rebuilds the
  documented context independently, so a silent layout change fails it, and
  it shows a well-formed container under the weakened r1 profile is refused
  even though the A2ONT API itself decodes it. AEAD would reject a mismatch
  regardless.
- A2ONT output never reaches the canonical parser before AEAD auth (unlock
  pipeline ordering; `no_plaintext_or_transform_markers_on_disk`).
- The decode boundary fuzzed under ASan+UBSan (`fuzz_a2ont`): 0.9.1's
  libFuzzer campaign ran it 1.60 billion times and then 215 million times on
  the final code, 0 findings (details in `TESTING_AND_FUZZING.md`; the first
  campaign, 2026-07, ran 500k executions when this code sat in a separate
  bridge file). Its minimized corpus is replayed by every test run
  (`fuzz_replay_a2ont`).

## 7. Honest boundary restated

A2ONT reduces at-rest structure and provides whole-output dependency. It does
**not** provide confidentiality, does not resist a co-located cache
side-channel adversary during the pre-AEAD window (not constant-time; out of
scope per its spec), and statistical-randomness passes on its output are
leakage-reduction evidence, **not** proof of secrecy. AEAD after A2ONT is
mandatory and is where secrecy and integrity live.
